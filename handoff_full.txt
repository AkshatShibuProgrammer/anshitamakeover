# 1. Original product plan

The site was planned as a luxury bridal makeup and beauty studio website with a clear editorial structure.

## Homepage purpose

The homepage should be a concise discovery and conversion page, not the entire website.

It should include:

1. Existing opening animation/preloader.
2. Hero section with:
   - Bridal positioning.
   - Strong visual.
   - Primary Services CTA.
   - Gallery/lookbook CTA.
   - Beauty Plan/booking CTA.
3. Occasion discovery:
   - Wedding/Bridal.
   - Engagement/Roka.
   - Reception/Cocktail.
   - Haldi/Sangeet.
   - Family/Bridesmaids.
4. Small featured services section:
   - Only strongest services.
   - Maximum approximately three to six cards.
   - Starting-from prices.
   - Links to dedicated service pages.
5. Small featured gallery/lookbook section:
   - Only strongest album cards.
   - No full gallery grid on homepage.
   - Clicking opens the hybrid album viewer.
6. Trust section near the bottom:
   - Sinha Family Group logo.
   - Accurate relationship/context.
   - Reviews or trust proof.
   - Location/travel positioning.
7. Final conversion section:
   - Beauty Plan.
   - Build Your Look.
   - WhatsApp enquiry.
   - Direct booking.

The homepage should not contain the complete services catalogue, full package catalogue, giant comparison matrices, or a long duplicated gallery.

- Correct media-type rendering.

## Interaction requirements

- Mobile-friendly.
- Touch/swipe-friendly.
- Keyboard-accessible.
- Escape closes viewer.
- Focus returns to invoking control.
- Visible close button.
- No confusing nested scrolling on mobile.
- Native page scrolling must not be hijacked.
- Reduced-motion mode must disable or simplify transitions.

# 4. Beauty Plan / booking flow

The generic retail cart concept was intentionally rejected in favor of:

- “Beauty Plan”
- “My Bridal Plan”

The exact final label can be chosen consistently, but it should not feel like a generic ecommerce cart.

Required behavior:

1. Shared top navigation button opens Beauty Plan/cart.
2. Users can add multiple services/packages.
3. Users can change quantities where applicable.
4. Users can submit:
   - Name.
   - Phone.
   - Email, optional.
   - City/location.
   - Event date.
   - Notes.
5. API stores a BookingEnquiry.
6. Server resolves submitted IDs against active services/packages.
7. Server recalculates the total.
8. Browser-provided `estimated_total` must never be trusted.
9. Invalid/inactive IDs must not generate fake totals.
10. Successful enquiry provides:
    - Enquiry reference.
    - WhatsApp handoff.
11. Admin can:
    - View enquiries.
    - Change status.
    - Archive enquiries.

Existing booking API:

```text
POST /api/booking/
```

Admin enquiry page:

```text
/admin-portal/enquiries/
```
